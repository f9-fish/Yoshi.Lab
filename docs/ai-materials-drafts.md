# 教科書本文マスター → AI教材生成候補（Spark対応・下書き段階）

## 作成済みのシート
既存スプレッドシート `1QK19vwZlG5_7uURKLi33W1zutKtAin5sKo8kbULVTrU` に既存タブを維持したまま
- 左端「教科書本文マスター」（sheetId=2093116001）：1文1行。原文ID、科目、単元ID、Part、文番号、英語、日本語訳、メモ、生成対象、備考
- 「AI生成候補」（sheetId=2093116002）：5種類の問題を審査するステージング表。「要確認」「採用」「却下」「転記済」
を追加。本文マスターにはユーザー提供の Lesson 7 PUS の12文と和訳を初期登録済み。

## 設計
1. 先生が本文マスターへ原文IDが一意となるよう本文を登録。教材は公開JSONやGitHubにコピーしない。
2. 先生が対象Partの行を選択して `prepareAIMaterialsMaster` を実行。空欄の原文IDと「生成対象」を補完する（既存値は上書きしない）。次に `previewAIMaterialsDrafts` で対象文数を確認。
3. 先生が外部AIへの教科書本文送信について学校の取扱規程・APIのデータ利用条件・著作権・費用を確認し、明示的に承認したときだけAPIキーを登録。
4. `generateAIMaterialsDrafts` を実行。**自動トリガーは作らない**。対象Partの本文だけがGemini APIへ送信され、返答はJSONとして検証し、単語・熟語と他の4種類を**2回のAPI呼び出しで別々に生成・検証**し、5種類すべての候補を「要確認」で新規行に追加。単語15〜25語、熟語5〜10件を目安に抽出（本文に該当語が少ない場合は水増ししない）。文法5〜8問、本文Q&A5〜8問、T/F5〜8問、Discussion3〜5問を目安とする。
5. 「採用」や「却下」は人による確認の印としてのみ扱う。**既存の「問題集」「英単語」「英C本文QA」等への自動転記とGitHub同期・アプリ公開は一切しない**。次フェーズで種類ごとの登録仕様・重複判定・公開前テストを整える。
6. True / False と Discussion はまだアプリ側の学習モードがないため、候補の作成・審査のみ。

## 既存Apps Scriptへの導入（まだ未適用）
`apps-script/ai-materials-drafts.gs` を既存プロジェクトへ追加ファイルとしてコピーし、同名の既存ファイルがないことを確認。Script Properties：
- `AI_MATERIALS_GEMINI_API_KEY`：APIキー。コードやスプレッドシートに書かない
- `AI_MATERIALS_MODEL`：利用契約上有効なGeminiモデルID（モデルの提供状況を確認）
- `AI_MATERIALS_EXTERNAL_SEND_APPROVED=true`：学校で利用可能と判断し、外部送信を承認したときのみ設定

APIキーや承認フラグが未設定ならAPIを呼ばない。API利用料金、データ取り扱い、送信できる本文の範囲を確認すること。

## 防御と限界
- 既存同期のコード・トリガー・公開フラグを変えない。
- 明示的な実行とScript Properties承認が必要。最大40文を1回の送信対象とし、テキストレスポンスはJSONとして検証。
- sourceIds照合、5種存在チェック、回答必須、T/F形式、生成内の重複キー確認。既存候補の同一Lesson・Part・種別・設問とも重複登録を避ける。どちらかのAPI呼び出し／検証に失敗した場合は候補を一切追加しない。
- 原文やAPI応答本文をログへ出さない。Script PropertiesへAPIキーを隔離。
- AIが本文を正確に理解した保証はない。先生による英語・事実・学習目標の確認が必須。
- 人手確認後の自動転記、学習アプリ用T/F・Discussionの追加、初回の実サービス試験は未完了。
- Firebase Spark/Blazeとは独立しており、Google Apps Script＋外部APIの利用条件が適用される。

## 初期テストの注意

- Apps ScriptのソースはドラフトPRにのみあり、本番のApps Scriptプロジェクトへはまだコピーしていない。APIキー未設定・外部送信未承認のままでは生成されない。
- Geminiへの外部送信を承認する前に、学校の著作物の取扱い、APIサービスのデータ使用条件・料金・利用規約を確認する。
- Apps Scriptエディターから実行すると対象の行選択を認識できない環境もある。その場合は実行方式の改善が必要で、誤ったPartを推測して送信しない。

## STEP 3：採用候補の安全な転記

追加ファイル：`apps-script/ai-materials-transfer.gs`。**既存ファイルは上書きしない。** Apps Scriptの同一プロジェクト内に新規スクリプトファイルを追加する。

- `AI生成候補` の **レビュー状態(N列) が `採用`** の行のみ対象。
- `previewApprovedAIMaterials()` は全転記先のヘッダーや必須値を検証し、種別ごとの予定件数をログ表示する。**この関数は読み取り専用。**
- `transferApprovedAIMaterials()` は検証後、採用行だけを転記する。成功した候補のレビュー状態を `転記済` に変更する。
- 転記された教材の公開状態はすべて `下書き`。既存同期関数は呼び出さない。
- 既存シートの既存行を上書きしない。英単語は科目＋Lesson＋Part＋語句、Q&Aは科目＋Lesson＋Part＋英文質問／生成ID、専用下書き表は候補IDで重複チェックする。重複は追加せず、候補の `採用` を保留するので手動確認する。

| 教材種別 | 行き先 | 注意 |
| --- | --- | --- |
| 単語・熟語 | `英単語` | G列の公開設定=`下書き`。カタカナ読みは未入力。 |
| 本文Q&A | `英C本文QA` | L列の公開状態=`下書き`。Part内で採番。 |
| 文法・穴埋め | `AI文法下書き` | 教科書用の日本語訳が生成候補にないため、既存`問題集`へ直接転記しない。訳を追記・確認後に次の工程で対応。 |
| True / False・Discussion | `AI発展教材下書き` | アプリ側の新モードが完成するまでは隔離。 |

**初期検証**：架空の採用候補5件を用いて、5種類・4転記先への登録、`転記済`への状態更新、未採用候補の保持、同じ処理の再実行で二重登録されないことをモックテストした。Google Sheets本番への転記はまだ行っていない。

注意：Google Sheetsの複数タブへの一括書き込みはトランザクションではない。途中でエラーが出た場合、転記先に既に追加されている行と候補の状態を確認すること。基本的な重複検出はあるが、同じ内容を微妙に書き換えた場合や、人が転記先を編集した場合の全ケースは自動では保証できない。

## STEP 4：英単語・本文Q&Aの公開前チェックとレビュー用同期

追加ファイル：`apps-script/ai-material-release-review.gs`。既存Apps Scriptに新規ファイル `ai-material-release-review` として追加し、`previewAIMaterialRelease()` から実行する。

### 使い方
1. 採用・転記済み教材を担当教員が校閲し、既存の `英単語` のG列、`英C本文QA` のL列で公開したい行だけ `公開` にする。
2. `previewAIMaterialRelease()` を実行。**読み取りのみ**で、公開対象の件数・必須項目・同一Part内の重複を検査する。エラーがあれば同期は禁止。
3. GitHubで事前に専用の検証用ブランチを作成し、Script Propertiesに `AI_RELEASE_REVIEW_BRANCH` を設定する（例：`review/ai-materials`）。`main`、`master` はスクリプトで拒否する。必要に応じて `AI_RELEASE_GITHUB_REPO`、`AI_RELEASE_GITHUB_TOKEN` を登録。既存の `PAIR_QA_GITHUB_REPO` / `PAIR_QA_GITHUB_TOKEN` があれば代用可。**トークンはGitHubやチャットに書かない**。
4. `syncAIMaterialReleaseReview()` を**手動で**実行。検証用ブランチで `vocabulary.json`、`pair_text_qa.json`、`pair_text_qa_catalog.json` を1コミットでまとめて同期する。mainへの同期はしない。
5. 検証用ブランチのJSON差分をレビュー。必要な場合だけ人手でPRをマージし、実際のアプリのQ&Aバックエンドやスナップショット側の運用と整合させる。

`AI文法下書き`、`AI発展教材下書き` は今回の同期対象外。アプリ側の対応完了・追加校閲までは公開しない。

### 現在の試験結果（2026-11-10）
- 実際のGoogle Sheets上の公開件数：英単語62件（5単元）、英C本文Q&A21件（4Part）
- GitHub mainの現在の教材JSONと件数が一致
- 下書き状態のLesson 8は出力から除外
- JSON生成関数のモック検証6件成功：公開行数、公開教材エラーなし、下書き除外、重複検出、下書き追加への耐性、必須項目欠落検出
- 検証用GitHubブランチへの書き込みは**まだ実行していない**。Apps Scriptへの実運用導入・本番公開も未実施。

**重要**：本番の既存単語同期（Google Apps Script側、リポジトリでソース未確認）が有効な場合、ステータスを `公開` に変えるだけで既存トリガーが別途同期する可能性がある。意図しない本番反映を避けるには、現行トリガーを確認してから公開ステータスを変更すること。レビュー専用の最初の確認は公開設定を変更せずにプレビューする。

**注意**：この追加処理は既存の `syncEnglishTextQA` などを変更しない。英単語の公開JSONは既存の `vocabulary.json` と同じグルーピング形状（subject/id/name/words）で生成する。QAの生成形式は既存の本文QAと同じ。レビュー用GitHubブランチではGitHub上に公開問題が載るため、機密性のある問題の公開前テストには使わない。


## STEP 4：公開前レビューとGitHubへの追加同期

**アプリの通常学習で既存の単語を壊さないように、当初は英単語のみ追加専用の同期に限定する。**

### 単語
\`apps-script/ai-vocabulary-publish.gs\` を既存Apps Scriptへ新規ファイルとして追加する。

Script Properties：
- \`AI_VOCAB_GITHUB_REPO=f9-fish/Yoshi.Lab\`（既存の \`PAIR_QA_GITHUB_REPO\` と共用可）
- \`AI_VOCAB_GITHUB_TOKEN\`（既存の \`PAIR_QA_GITHUB_TOKEN\` と共用可。ただしコード・シートにキーを書かない）
- \`AI_VOCAB_GITHUB_BRANCH=main\`（省略時 main）
- \`AI_VOCAB_SYNC_APPROVED=true\` は、**同期対象をレビューして公開すると決めたときだけ**登録する。

操作：
1. AI生成候補から採用した語が \`英単語\` の「下書き」に転記されたことを確認する。
2. 英単語の「読み方」列を含む内容を校正し、公開する行だけ G列を「公開」に変更する。
3. \`previewEnglishVocabularyPublish()\`：GitHub の現在の \`vocabulary.json\` と照合し、新規語の件数・グループ・読み方未入力を表示する。GitHubやシートは変更しない。
4. 公開を明示承認した後 \`syncEnglishVocabularyPublish()\` を手動実行。新規公開語だけ \`vocabulary.json\` に追加し、既存語の内容と配列順序は維持。
5. GitHub Pagesの反映を確認したらYoshi.LabでLesson・Partの単語表示と正解判定を手動確認する。

**重要**：すでに別のスプレッドシート同期が \`vocabulary.json\` を更新している場合、**両方を同時に運用しない**。既存同期が動くと差分追加分を上書きする可能性があるため、既存同期側への統合を先に検討する。今回作成した同期は、既存語の削除・修正や下書き状態への戻し（取り下げ）を反映しない「追加専用」である。

初期状態の照合結果：2026-11-10時点で「英単語」公開62語と main の \`vocabulary.json\` 62語が、語句・訳・ヒント・読み方について一致していた。新規Lesson 8の語は下書きのまま。

### 本文Q&A
既存の \`previewEnglishTextQA()\` と \`syncEnglishTextQA()\` を利用する。初回は必ずプレビューし、教材ごとの本文根拠や別解・ヒント、問題番号を確認してから「公開」にする。

### 文法・穴埋め / True / False / Discussion
\`AI文法下書き\` と \`AI発展教材下書き\` に隔離したまま。既存\`問題集\`では日本語訳・穴埋め形式が足りないため、自動公開しない。T/FとDiscussionはアプリ側の受け皿がまだない。

### 検証範囲

- 公開済み語が1件存在するサンプルJSONに新語を追加し、再実行時に二重追加が起きないこと、既存語の意味の差異を検出・拒否することをローカル関数テストで確認した。
- **Apps ScriptからGitHubへ実際に書き込む同期は未実施**。
