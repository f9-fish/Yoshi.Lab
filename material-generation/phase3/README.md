## 認証の実装

`ScriptApp.getIdentityToken()` が発行するGoogle IDトークンをAuthorizationヘッダーだけで送ります。JWTの署名はGoogle公式 `google-auth-library` で検証し、issuer、正確なApps Script OAuth client ID（audience）、期限、email_verified、subも確認します。単なるJWTデコードや申告メールは認証に使いません。

Firebase Adminは `getUserByEmail` で既存ユーザーを探し、確認済みメール・無効化されていないこと・FirebaseのGoogle provider UIDがIDトークンのsubと同じこと・`teacherUids/{uid}===true` を毎回確認します。メールが再割当てされた別のGoogleアカウントが旧教員権限を継承しないようにしています。Firebaseユーザー作成やDBへの書き込みはありません。

ジョブは教員UIDのハッシュで所有者を固定。他教員のジョブIDを指定しても取得・生成・計画を拒否します。本文やGeminiへUID・メール・本人トークンは渡しません。本人トークンはDrive・Script Properties・ログに保存しません。

実際のOAuth audience、トークン発行者、トリガー実行者、Google権限付与、サービスアカウントの読み取り権限は未確認です。管理者確認前には接続しないでください。Firebase IDトークン用の既存APIを、Apps Scriptのトークンで迂回する方式ではありません。

## キュー・二重実行・復旧

- 同一教員・本文ハッシュ・設定ハッシュ・対象テストIDは同じジョブID。同じ登録を繰り返しても新規生成しない。
- 本文変更・設定変更・明示的revision変更は別ジョブ。元の結果は上書きしない。
- 1要求で新しい種類を最大1件だけ生成。成功した種類のチェックポイントを保持し、再開では呼び直さない。
- 認証サーバーのリビジョンを指定してstepを要求。同じリビジョンの再送・応答消失は同じ結果を返し、有料生成を繰り返さない。
- サーバーのファイル排他とApps ScriptのScriptLockを使用。UIの確認ダイアログはロック取得前に出し、確認後に再取得・再読込する（Apps Scriptはダイアログ中にロックを保持しないため）。
- 手動二重クリックも最初に見たリビジョンを照合し、他処理が進んでいれば新しい生成をせず状態だけ取得する。
- サーバーで教員ごとに1日10回の種類生成を初期上限とし、登録は1日20ジョブまで。日付は日本時間。同時要求でも排他的に数える。自動再試行はしない。
- Apps Scriptの自分用キューはUserPropertiesに最大50件のIDだけを保持。内容は私有Drive JSONに保存し、Script Propertiesの1値の容量制限へ押し込まない。
- `mgRunWorker` は選択ジョブを1種類進める。`mgChooseJob` は自分のキューから選ぶ。`mgTick` は自分の生成待ちキューを1種類進める任意の時間トリガー用関数で、このコードからトリガーは登録しない。
- 時間トリガーは作成者の権限で動く。各教員が所有するテストプロジェクト・私有フォルダ・キューで実行し、全員分を所有者の権限で代行するWebアプリは作らない。
- 生成失敗はエラーとして保存し、明示的な再試行の費用確認が必要。生成中のまま応答が未確定なら自動再試行しない。

### サーバープロセス停止の復旧

FileStoreは永続ボリュームを共有する単一サーバー向けです。Cloud Run/Functionsの一時ディスクを永続保存とみなしてデプロイしてはいけません。ロックファイルを時間だけで自動削除せず、処理中または残存ロックとして停止します。

管理者はサーバー停止を確認し、状態ディレクトリをバックアップ、残存ロックと該当ジョブ・料金の成否を確認します。成否不明を承認なしに再生成しません。再試行が必要と判断した場合だけ、状態・チェックポイントを保持したまま該当ジョブをエラー状態として復旧し、確認済み残存ロックを解除します。サーバー再開後は明示的な費用確認で再試行します。保存できなかった有料応答の完全なexactly-once保証はできません。自動で再課金しない設計です。

サーバー状態・Driveジョブには保管期間とバックアップを設定し、50件を超える前に管理者が終了ジョブを保管・キュー整理してください。自動削除機能は今回ありません。

## 追記と部分成功からの再開

対象はテストブックの「英C本文QA」「英作文問題」「AI発展教材下書き」の3タブです。新しい正誤タブは作りません。既存Discussionは保持します。

1. 本文を再読込し、登録時の本文ハッシュをサーバーで照合。
2. 対象タブの実ヘッダーと既存行を読み、Phase 2の追記計画を作る。語彙候補は結果内に残すだけで追記しない。
3. 教員がテスト用IDと差分を確認した後、ロックを取り直して再計画。確認中に変わっていれば停止。
4. 各タブの直前にも本文・既存行のハッシュを照合し、既存行変更0・削除0・新規行は要確認だけであることを確認。
5. Sheets APIの `valueInputOption:RAW` と `insertDataOption:INSERT_ROWS` で最終既存行を基準に末尾追記。既存セルにsetValuesやupdateはしない。
6. 追記後も既存行の値と新規行の存在を照合し、成功したタブをDriveジョブに記録。
7. 一部だけ成功、または応答消失したら再読込・再計画。候補IDと内容が同じ行は追加せず、未追記分だけ実行。同じIDで内容が変わっていれば教員編集として停止し、上書きしない。

ScriptLockは同一Apps Scriptプロジェクトにしか効かず、手動編集や別プロジェクトを完全にロックできません。既存セルを上書きしないAPI方式を使い、観測した競合では停止します。複数タブの完全なトランザクションや自動ロールバックは行いません。部分成功した要確認行を勝手に削除しません。

## 実Geminiによる小説型英作文の評価手順

今回は実APIを呼んでいません。以下は管理者がテスト接続を承認した後の手順です。

1. 架空の原稿を3種類（出来事・科学説明・学校生活）、ジャンルを2種類（ミステリー・青春）用意する。まず1ケースで検証し、拡大して計6ケース×10文を評価する。
2. 品質評価時は `counts:{vocabulary:0,qa:0,writing:10,trueFalse:0,discussion:0}` にし、余分な有料生成や追記をしない。正確なモデルID・日時・本文ハッシュ・設定を記録する。既存上限は勝手に緩めない。
3. 生成結果から `writingReview(job.report)` で評価票を作る。初期値は全項目未評価・公開不可。実行教員の私有領域に保存し、教科書本文や個人情報を公開リポジトリへ置かない。
4. 教員が各文の和英対応・文法・指定語の自然さ・単独設問の明確さ・別解・ヒントを確認し、全体の起承転結・意外性・独立性・難易度を採点する。可能なら二人で独立にレビューする。
5. 評価票の8観点を0〜2点で記録。意味の逆転・文法誤り・指定語不成立・原文や既存例文の複製は重大不備として、総点にかかわらず不採用。目安14/16以上でも教員確認なしで承認しない。
6. 修正文と理由を保存。別解は既存writing-training.jsの正規化と指定表現条件でも確認する。物語の前後を知らないと答えられない日本語は直す。
7. 問題数不足・生成失敗・不自然さの割合をまとめ、プロンプト変更後も同じケースで再評価する。今回の手作りモックを実AIの品質実績と扱わない。

品質評価・テスト追記が完了しても、本番への接続はこの実装ではできません。英単語同期の実コード・承認工程・本番公開手順を確認し、別の変更と管理者承認が必要です。
